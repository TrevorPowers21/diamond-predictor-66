## TRACK 1 — The eligibility / class-consistency fix (IN FLIGHT)

### Branch
`feature/eligibility-class-consistency` (cut off `origin/staging`). **Part A committed; Part B pending.**

### The bug (verified)
The same player shows different class/eligibility on different surfaces.
- **Report:** Cole Johnson (Georgia) — **JR** on Roster Management + the player-profile home header, but **SO** on the 2027 projections (SO is correct).
- **Root cause, confirmed by investigation:**
  1. `class_year` is the source of truth for real class (Cole = `"FR"`). `class_transition` is *derived* from it (`FR→FS, SO→SJ, JR→JS, SR→GR`) and is **double-duty**: a **projection input** (carries the developmental factor — freshmen develop more) AND the **eligibility display** (2nd letter = next-season class).
  2. `predictionEngine` **defaults `class_transition` to `"SJ"`** when missing (`|| "SJ"`) → `SJ`'s 2nd letter is `J` → **JR**. This default predates having real class data; that's *why* the coach override exists.
  3. `projectedEligibilityClass(classYear, classTransition)` checked the **transition FIRST**, so a stale `"SJ"` **overrode** a correct `class_year="FR"`.
  4. The GM roster/header read a **frozen `class_transition` snapshot** captured on the build row at add-time (stale `"SJ"`); the projections page reads the **live** prediction (Cole's 2027 rows were corrected to `"FS"` → SO). Cole's own predictions are internally inconsistent: **2026 regular = `"SJ"` (stale), 2027 = `"FS"` (correct)**.

### Verified prod audit (blast radius — segment or it's ~2× inflated)
- 75 tables; `players.division` = D1 (26,110) / NJCAA_D1 JUCO (5,300).
- `player_predictions.season` = only **2026 + 2027** (no older).
- **~50% of the `players` table is historical** (15,738 of 31,412 have no 2026 prediction) → **always filter to "has a 2026 prediction."**
- **Stale-`SJ` problem = 7,970 players, 100% D1, 0 JUCO** → the real fix target.
- **Null `class_year` = ~95% JUCO** (5,269 JUCO vs 251 D1).
- **JUCO uses class for DISPLAY only** — its projection path (`jucoReturnerPitcherProjection.ts` + JUCO hitter branch) deliberately skips class_transition/dev-factor. So the JUCO refresh never affects JUCO projections.

### Trevor's decisions on the fix

- **Precedence:** explicit coach override → `class_year` → default transition. Overrides are **rare** (redshirts / known-different eligibility). Should later expose a per-player eligibility override on player pages (currently only Team Builder / GM `eligibility_class`).
- **Fix the code but DON'T run precomputes now** — projections get finalized after the portal closes over multiple sessions (branches to clean up), so the corrected dev factor lands automatically at finalization.
- **JUCO class-data (C):** future; low-stakes (display only); needs refreshing eventually; investigate/confirmed class is display-only for JUCO. ✅ done.
